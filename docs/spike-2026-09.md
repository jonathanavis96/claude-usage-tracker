# Spike: does the tick probe work, and does it agree with the passive join?

Date: 2026-09-05/06. Status: complete. This is the acceptance check named in
the design spec (Testing section). Raw rows: `out/spike-probes.jsonl` (gitignored)
and the first row committed as `history/probes.jsonl`; the passive daily table
is `out/spike-passive.txt`.

## Result in one line

The probe works, costs about 1% of a 5-hour window per run, and agrees with the
passive join to within about 13% once both are expressed in API dollars per 1%
of window. Expressed in raw tokens they disagree by 7x, because the meter is
cost-weighted and the two workloads have opposite cache mixes.

## The probe (Sonnet 5, effort low, Dave account, Max 20x)

| Field | Value |
|---|---|
| Account | dave (`~/.claude-dave` on gs) |
| Prompts used | 10 (unique 42k-token payloads) |
| Elapsed | 1,430 s |
| Tick observed | 2% to 3% |
| Tokens between ticks | input 18, output 45, cache read 87,021, cache write 403,629 |
| Tokens per 1% | 490,713 |
| API value per 1% | $1.03 (Sonnet 5 list prices, `data/prices.json`) |
| Window cost of the run | 1% of the 5-hour window, 0.1% of the 7-day window |

Six attempts were needed to get here. What each one taught:

1. **Idle guard hung.** `resets_at` jitters by sub-second amounts and crosses
   minute boundaries between reads, so a raw string compare saw a "reset" on
   nearly every pair of samples. Fixed with `same_reset()` (60 s tolerance),
   shared by the probe and the passive join. The same bug had truncated the
   passive history to 2026-08-18; it now runs from 2026-07-30.
2. **Endpoint rate limit.** `GET /api/oauth/usage` returns 429 after about 3
   reads per minute per token, and its `Retry-After` can be `0`. The client
   now sleeps `max(Retry-After, schedule)` with schedule 30/60/120/240/480 s and
   the probe reads the meter once per prompt with a 60 s settle.
3. **Small prompts are invisible.** The original 13.7k-token prompt moved the
   meter 0% over 11 prompts. One 277k-token prompt ticked 1% at once.
4. **Identical prompts get cached.** The same 277k prompt re-sent became a
   287k cache *read* and barely registered. Every probe prompt is now unique
   (`probe_prompt(salt, i)`, 9,000 pseudo-random words, about 42k tokens).
5. **Cross-window abort.** One run straddled the 5-hour reset and was
   correctly discarded (exit 4).
6. Attempt 6 is the row above.

## The passive join (masterrig, Jonathan's account)

39 days of daily rates from 2026-07-30. Cache mix over the period: 96.5% cache
read, 3.0% cache write, 0.5% output, 0.01% input. Median tokens per 1%:

| Period | Plan | Median tokens per 1% | Days |
|---|---|---|---|
| before 2026-08-18 | Max 5x | 1,855,247 | 11 |
| from 2026-08-18 | Max 20x | 3,675,348 | 19 |

Observed 5x to 20x ratio: about 2.0 (2.6 with the join's own estimator). The
published ratio is 4. The passive series cannot pin it: daily values swing 4x
day to day, several days have under 10 qualifying intervals, and usage from
other machines on the same account deflates the token count without deflating
the meter. **Ruling:** the page uses the published 1:5:20 plan ratios and
cites the measured 2 to 2.6 in the caveats.

## Probe vs passive, same plan

| Expression | Probe (Sonnet 5, 82% cache write) | Passive (97% cache read) |
|---|---|---|
| Tokens per window | 49 M | 368 M |
| API dollars per window at Sonnet 5 prices | $103 | $116 |

The 7x token gap is the cache mix: a cache-write token costs 12.5x a
cache-read token and the meter charges accordingly. In dollars the two agree
to 13%, which is inside the passive series' day-to-day noise. So the invariant
Anthropic's meter tracks is API value, not tokens.

**Ruling (page arithmetic):** the publisher computes dollars per 1% from each
probe row (tokens by class times list price) and converts it to tokens per
window using the passive join's real cache split, so the page's "tokens per
window" describes a working session's mix rather than the probe's. The
dollar figure is also published as `api_value_per_window`. Detection runs on
the converted series, which moves in the same ratio as the dollar series
while the price table is fixed. Cost if wrong: if Anthropic re-weights cache
classes without changing prices, the probe's mix would drift against the
passive mix and the page would over- or under-state tokens by the drift.

## Weekly cost and cadence

One probe costs 1% of a 5-hour window and 0.108% of the 7-day window. Two
probes a day, models rotated, is 14 probes a week, about 1.5% of the weekly
allowance on the probe account, spread across Dave and Jono Work. That is the
cadence installed in cron (`05 04,16 * * *`). Opus and Fable probes cost the
same number of prompts only if the dollar invariant holds across models; if it
does, a Fable probe ticks in about 2 prompts and could stand in for all three.
That is checked by the next two probe slots and is not assumed here.

## Ruling 2026-09-06

Decision: probe ONE model, Sonnet 5, about once a week. Every other model's
tokens_per_window is derived, not probed -- the dollar invariant established
above means one model's `api_value_per_window` plus that model's own price
table entry and the passive class split is enough to compute any other
model's rate (`api_value_per_window / blended_price_per_token(split, price)`).
This is why Opus 5 and Fable 5.1 previously showed nothing on the page: the
publisher only emitted a `rates[model]` entry for a model with its own probe
row. `build_public_json` now emits one for every model in `prices.json`,
marked `"source": "probe"` for the model actually probed and `"derived"` for
the rest. Change detection moved off calendar-day buckets onto the raw,
sample-based dollar series (see `tracker/detect.py`) since a weekly cadence
has no daily buckets to smooth over. The rotation described above and the
twice-daily cron cadence are superseded by this ruling.

## Ruling 2026-09-06 (meter weight)

Decision: the dollar invariant is not one dollar-per-token price relative
across models -- the 5-hour meter charges some models more per list dollar
than others. Calibration (`data/effort_matrix.json` `_meta.runs` and
`_meta.usage_deltas`, three repeats per model/effort, 2026-09-05/06) shows
Fable 5.1 moving the meter 1.6x to 2x harder than Sonnet 5 or Opus 5 for the
same list-dollar spend: $1.00 of Sonnet 5 list value moved the meter about
1%, while $10.26 of Fable 5.1 list value moved it about 16% -- 1.6x the
list-dollar-for-meter-percent rate Sonnet showed, inside the 1%-quantised
noise floor of the delta readings. Anthropic states Fable consumes usage at
twice the Opus rate, which is the harder number and the one adopted: each
model in `data/prices.json` now carries a `meter_weight` (Sonnet 5 and Opus 5
at 1.0, Fable 5.1 at 2.0), and `usd_per_pct` multiplies a probe row's
list-dollar value by its own model's weight before it enters the
model-agnostic dollar invariant, so a probe on Fable and a probe on Sonnet at
the same meter reading now publish the same `api_value_per_window`. This is
a placeholder ratio pending a direct Fable probe -- the calibration run above
is consistent with 2.0 but does not itself prove it to more precision than
its quantisation allows.

## Ruling 2026-09-06 (Fable meter weight, measured)

The 5-tick Fable 5.1 probe on Dave (17 prompts, ticks 8 to 13, prose payload) spent $1.081 of list value per 1%; the Sonnet 5 5-tick probe the same morning spent $0.979. Ratio 0.91, inside the probe's roughly 10% error, so `meter_weight` for Fable is set to 1.0: for cache-write-heavy traffic the meter follows list prices. The output-heavy calibration cells (Fable max: $5.10 list for 9%) still imply about 1.6x to 2x, so output tokens may carry a higher weight on Fable than list price. Unmeasured; a dedicated output-heavy probe would settle it. Note the published rates are dominated by cache reads (97% of the passive split), whose meter weighting no probe has measured directly for any model.
