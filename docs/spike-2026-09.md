# Spike: does the tick probe work, and does it agree with the passive join?

Date: 2026-09-05/06. Status: complete. This is the acceptance check named in
the design spec (Testing section). Raw rows: `out/spike-probes.jsonl` (gitignored)
and the first row committed as `history/probes.jsonl`; the passive daily table
is `out/spike-passive.txt`.

## Result in one line

The probe works, costs about 1% of a 5-hour window per run, and agrees with the
passive join to within about 13% once both are expressed in API dollars per 1%
of window. Expressed in raw tokens they disagree by 7x, because the meter is
cost-weighted and the two workloads have opposite cache mixes.

## The probe (Sonnet 5, effort low, Dave account, Max 20x)

| Field | Value |
|---|---|
| Account | dave (`~/.claude-dave` on gs) |
| Prompts used | 10 (unique 42k-token payloads) |
| Elapsed | 1,430 s |
| Tick observed | 2% to 3% |
| Tokens between ticks | input 18, output 45, cache read 87,021, cache write 403,629 |
| Tokens per 1% | 490,713 |
| API value per 1% | $1.03 (Sonnet 5 list prices, `data/prices.json`) |
| Window cost of the run | 1% of the 5-hour window, 0.1% of the 7-day window |

Six attempts were needed to get here. What each one taught:

1. **Idle guard hung.** `resets_at` jitters by sub-second amounts and crosses
   minute boundaries between reads, so a raw string compare saw a "reset" on
   nearly every pair of samples. Fixed with `same_reset()` (60 s tolerance),
   shared by the probe and the passive join. The same bug had truncated the
   passive history to 2026-08-18; it now runs from 2026-07-30.
2. **Endpoint rate limit.** `GET /api/oauth/usage` returns 429 after about 3
   reads per minute per token, and its `Retry-After` can be `0`. The client
   now sleeps `max(Retry-After, schedule)` with schedule 30/60/120/240/480 s and
   the probe reads the meter once per prompt with a 60 s settle.
3. **Small prompts are invisible.** The original 13.7k-token prompt moved the
   meter 0% over 11 prompts. One 277k-token prompt ticked 1% at once.
4. **Identical prompts get cached.** The same 277k prompt re-sent became a
   287k cache *read* and barely registered. Every probe prompt is now unique
   (`probe_prompt(salt, i)`, 9,000 pseudo-random words, about 42k tokens).
5. **Cross-window abort.** One run straddled the 5-hour reset and was
   correctly discarded (exit 4).
6. Attempt 6 is the row above.

## The passive join (masterrig, Jonathan's account)

39 days of daily rates from 2026-07-30. Cache mix over the period: 96.5% cache
read, 3.0% cache write, 0.5% output, 0.01% input. Median tokens per 1%:

| Period | Plan | Median tokens per 1% | Days |
|---|---|---|---|
| before 2026-08-18 | Max 5x | 1,855,247 | 11 |
| from 2026-08-18 | Max 20x | 3,675,348 | 19 |

Observed 5x to 20x ratio: about 2.0 (2.6 with the join's own estimator). The
published ratio is 4. The passive series cannot pin it: daily values swing 4x
day to day, several days have under 10 qualifying intervals, and usage from
other machines on the same account deflates the token count without deflating
the meter. **Ruling:** the page uses the published 1:5:20 plan ratios and
cites the measured 2 to 2.6 in the caveats.

## Probe vs passive, same plan

| Expression | Probe (Sonnet 5, 82% cache write) | Passive (97% cache read) |
|---|---|---|
| Tokens per window | 49 M | 368 M |
| API dollars per window at Sonnet 5 prices | $103 | $116 |

The 7x token gap is the cache mix: a cache-write token costs 12.5x a
cache-read token and the meter charges accordingly. In dollars the two agree
to 13%, which is inside the passive series' day-to-day noise. So the invariant
Anthropic's meter tracks is API value, not tokens.

**Ruling (page arithmetic):** the publisher computes dollars per 1% from each
probe row (tokens by class times list price) and converts it to tokens per
window using the passive join's real cache split, so the page's "tokens per
window" describes a working session's mix rather than the probe's. The
dollar figure is also published as `api_value_per_window`. Detection runs on
the converted series, which moves in the same ratio as the dollar series
while the price table is fixed. Cost if wrong: if Anthropic re-weights cache
classes without changing prices, the probe's mix would drift against the
passive mix and the page would over- or under-state tokens by the drift.

## Weekly cost and cadence

One probe costs 1% of a 5-hour window and 0.108% of the 7-day window. Two
probes a day, models rotated, is 14 probes a week, about 1.5% of the weekly
allowance on the probe account, spread across Dave and Jono Work. That is the
cadence installed in cron (`05 04,16 * * *`). Opus and Fable probes cost the
same number of prompts only if the dollar invariant holds across models; if it
does, a Fable probe ticks in about 2 prompts and could stand in for all three.
That is checked by the next two probe slots and is not assumed here.

## Ruling 2026-09-06

Decision: probe ONE model, Sonnet 5, about once a week. Every other model's
tokens_per_window is derived, not probed -- the dollar invariant established
above means one model's `api_value_per_window` plus that model's own price
table entry and the passive class split is enough to compute any other
model's rate (`api_value_per_window / blended_price_per_token(split, price)`).
This is why Opus 5 and Fable 5.1 previously showed nothing on the page: the
publisher only emitted a `rates[model]` entry for a model with its own probe
row. `build_public_json` now emits one for every model in `prices.json`,
marked `"source": "probe"` for the model actually probed and `"derived"` for
the rest. Change detection moved off calendar-day buckets onto the raw,
sample-based dollar series (see `tracker/detect.py`) since a weekly cadence
has no daily buckets to smooth over. The rotation described above and the
twice-daily cron cadence are superseded by this ruling.

## Ruling 2026-09-06 (meter weight)

Decision: the dollar invariant is not one dollar-per-token price relative
across models -- the 5-hour meter charges some models more per list dollar
than others. Calibration (`data/effort_matrix.json` `_meta.runs` and
`_meta.usage_deltas`, three repeats per model/effort, 2026-09-05/06) shows
Fable 5.1 moving the meter 1.6x to 2x harder than Sonnet 5 or Opus 5 for the
same list-dollar spend: $1.00 of Sonnet 5 list value moved the meter about
1%, while $10.26 of Fable 5.1 list value moved it about 16% -- 1.6x the
list-dollar-for-meter-percent rate Sonnet showed, inside the 1%-quantised
noise floor of the delta readings. Anthropic states Fable consumes usage at
twice the Opus rate, which is the harder number and the one adopted: each
model in `data/prices.json` now carries a `meter_weight` (Sonnet 5 and Opus 5
at 1.0, Fable 5.1 at 2.0), and `usd_per_pct` multiplies a probe row's
list-dollar value by its own model's weight before it enters the
model-agnostic dollar invariant, so a probe on Fable and a probe on Sonnet at
the same meter reading now publish the same `api_value_per_window`. This is
a placeholder ratio pending a direct Fable probe -- the calibration run above
is consistent with 2.0 but does not itself prove it to more precision than
its quantisation allows.

## Ruling 2026-09-06 (Fable meter weight, measured)

The 5-tick Fable 5.1 probe on Dave (17 prompts, ticks 8 to 13, prose payload) spent $1.081 of list value per 1%; the Sonnet 5 5-tick probe the same morning spent $0.979. Ratio 0.91, inside the probe's roughly 10% error, so `meter_weight` for Fable is set to 1.0: for cache-write-heavy traffic the meter follows list prices. The output-heavy calibration cells (Fable max: $5.10 list for 9%) still imply about 1.6x to 2x, so output tokens may carry a higher weight on Fable than list price. Unmeasured; a dedicated output-heavy probe would settle it. Note the published rates are dominated by cache reads (97% of the passive split), whose meter weighting no probe has measured directly for any model.

## 2026-09-06: output-heavy probe mode

Added `tracker.probe --payload {prose,output}` (default `prose`, unchanged behaviour). `prose` is the existing 12,000-word cache-write-heavy payload with a one-word reply. `output` sends `output_prompt(salt, index)` instead: a fixed template under 200 words asking for about 4,000 words of original narrative prose on a deterministic, unique (role, place, season) topic keyed by `random.Random(f"{salt}:{index}")`, the same no-repeat-no-cache-hit contract as `probe_prompt`. Nearly all the token spend in an `output` run lands as output tokens rather than cache writes, which is the traffic shape the calibration matrix (`_meta`) is made of. This exists to answer the open question from the previous ruling: the prose probe found Fable's meter following list price (ratio 0.91), but the output-heavy calibration cells imply 1.6x-2x -- so either the meter weights output tokens above list price on Fable specifically, or the calibration matrix is measuring something the prose probe cannot see. A 5-tick `output` probe on Fable, compared against the existing Sonnet 5 prose-probe rate, settles which. The probe row now records `"payload": "prose" | "output"` so the two traffic shapes never get averaged together by mistake; `publish.py` ignores the new key, so nothing downstream needed to change.

### 2026-09-06 ruling: the meter weights output tokens about 1.8x, not Fable

The output-heavy Fable probe ran at 12:06Z: 9 prompts, ticks 14 to 19, 10,379 output tokens plus 16,062 cache-read and 5,280 cache-write tokens per 1%, which is $0.589 of list value per 1%. The cache-write-heavy Fable probe an hour earlier cost $1.081 per 1% and Sonnet's $0.979. So one list dollar of output moves the meter 1.8x as far as one list dollar of cache write, on the same model, and Anthropic's "Fable uses twice the usage of Opus" is really "output-heavy work costs about twice what its list price suggests". Nine prompts over five ticks is coarse (about 11% quantisation), so 1.8 is a first estimate.

Ruling: `prices.json` carries a per-class `class_weight` (output 1.8, everything else 1.0) applied by `publish.py` in both `usd_per_pct` and `blended_price_per_token`, replacing the idea of a per-model weight for this effect (`meter_weight` stays at 1.0 for all three models and remains available). The same class weights are assumed for every model; input and cache_read weights are unmeasured. Practical effect on the published numbers: a model's tokens per window now depends on the passive split's output share, which is the traffic shape Jonathan's own sessions have.

## 2026-09-06: probe core rework (burst-first spans)

`tracker.probe` now needs `--expect-tokens-per-pct` on every run and uses it twice.
Prompt size: `payload_words_for(expectation)` makes one prose prompt about a tenth of a
tick (expectation / 10 / 3.47 tokens per word, clamped to 1,500 to 12,000 words; Sonnet
lands on the 12,000 cap, Fable at about 3,400), recorded on the row as `payload_words`.
An output payload keeps its fixed 4,000-word reply and records that. Bursts: every span,
the alignment span included, opens with one burst of concurrent prompts sized to 80% of
the expected span (expectation over the mean tokens per prompt seen so far, or the word
estimate before the first prompt), then singles until the tick; the old `--burst K` flag
is gone. A tick that lands inside a burst in a full span flags the row `early_tick`
(the span was shorter than expected, so the limit has probably fallen) and every later
burst drops to 50% of the span; a tick inside the alignment burst is not early when a
span is skipped, since the alignment span is a partial and the span it corrupts is the
skipped one. If the window's `resets_at` is within 20 minutes at the start, the probe
waits for the reset and, if the meter then reads 0.0, takes that as the first tick with
no alignment span (`reset_start` on the row). Defaults are now 3 measured ticks after 1
skipped span. Rows record `ticks`, `skip`, `settle_s`, `expect_tokens_per_pct`,
`payload_words`, `early_tick` and `reset_start`; `burst` and `overshoot` are dropped
(a burst that carries the meter past the final tick is an early tick, and the extra
percent stays in the division). `bin/probe.sh` passes the 09:39 Sonnet rate as a literal
expectation until the rotation supplies its own. A run that starts 20 to about 80
minutes before a reset still aborts on "window reset during probe", as before.

## 2026-09-06: automatic output class weight

The 1.8 above was hand-entered as the crude ratio of the two Fable rows' list
values per 1% (1.081 / 0.589). The publisher now maintains
`class_weight.output` itself (`tracker/weight.py`). `bin/output-probe.sh`
runs a 5-tick Fable probe with `--payload output` every Sunday 06:00 UTC; the
next daily publish takes the latest output row and the latest Fable prose row
and solves for the weight at which both read the same meter dollars per 1%,
which is the invariant `usd_per_pct` relies on:

    other_prose + w * output_prose = other_output + w * output_output

with `other` the row's non-output list value (the other classes' weights
applied). The crude ratio is the special case where the output row carries
no cache traffic; it carries about 12% of its list value as cache read and
cache write, so the same pair of 2026-09-06 rows solves to 1.95, and that is
the value now in `data/prices.json` (applied by the publisher on 2026-09-06
from the 12:06 output row against the 11:16 prose row, recorded under
`_output_weight`). Output rows are excluded from the dollar series, the
regime medians, change detection and the freshness check by their payload
tag (`tracker/rows.py`), and the rotation and drift medians use the same
filter.

Guard: a recomputed weight more than 30% from the current one is not
applied. The refusal is recorded against the pair of rows it came from, so
the daily publish alerts Jonathan once (through `tracker/alert.py`) rather
than every day until the next run. Accepting a refused value is a hand edit
of `class_weight.output` on every model in `data/prices.json`. The same
class weights are assumed for every model; input and cache_read remain
unmeasured at 1.0.

## 2026-09-06: rotation, expectation and drift confirm-by-rerun

`bin/probe.sh` no longer carries a model or a literal expectation:
`tracker/rotate.py` supplies both. The rotation is the fixed order Sonnet 5,
Opus 5, Fable 5.1, advanced from the last prose row (an outlier row still
took its turn; an output row never moves it). The expectation is the dollar
invariant run backwards: the median meter-dollar value per 1% of the last
four usable prose rows, any model, divided by the target model's blended
meter price per token for probe traffic (the class split of its own latest
prose row, or of the latest prose row when it has none) and its
`meter_weight`. Opus therefore gets an expectation before it has ever been
probed, and every model's expectation moves together when the limit moves.
Dry run on the history as of this ruling: Sonnet 527,647, Opus 211,059,
Fable 112,312 tokens per 1%, Opus next.

Drift is a new row more than 15% from the median of that model's last four
usable prose rows, in tokens per 1% (same model, same payload, so no price
conversion). The first burst-first Sonnet row (14:33, 579,819) against the
09:39 reading (467,779) is +24%: drift, and the case the rerun logic exists
for. On drift the wrapper reruns once on the same model with 2 ticks, using
the smaller of the median and the drifted reading as its expectation so the
opening burst cannot overshoot whichever turns out to be true. Then the pair
decides: a rerun within 15% of the earlier median makes the first row an
outlier, flagged in place with `"outlier": true` and ignored by the
publisher, the rotation medians and the weight pairing (the row itself
stays in history); a rerun within 15% of the drifted reading instead is a
change (two agreeing readings that both differ from the earlier median) and
both rows stand for the publisher's own change detection to step on;
anything else is inconclusive and flags nothing. Each outcome is one email
to Jonathan through `tracker/alert.py`. A rerun that writes no row leaves
the drifted row unflagged and exits with the rerun's code.

The 14:33 row is drift on real data and has not yet been confirmed or
rejected: the rerun is the next Sonnet slot's job, or a hand run of
`bin/probe.sh` from a Sonnet turn.
